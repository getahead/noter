# Common rules for every backend M1 worker (read with your own spec)

- Read: `CHARTER.md` (Engineering rules, Middle developers, BACKEND M1), `ROSTER.md`, `PLAN-be-m1.md` (decisions TL-1..TL-11, order, owners), then the repo's `CLAUDE.md`, `docs/DEVELOPMENT.md`, `docs/HARNESS.md`, your FEATURE spec in `docs/features/core/`, and the DESIGN-core sections it cites (`docs/DESIGN-core.md`: 3.1 Domain Model, 3.2 Component Model, 3.3 API Contracts, the `cpt-noter-dbtable-*` entries).
- Every shell starts with `export PATH=/opt/homebrew/bin:/usr/bin:$PATH NOTER_E2E_LOCK=$HOME/projects/noter-wt/.e2e.lock`. Orca: `/Applications/Orca.app/Contents/Resources/bin/orca`. `just setup` once in your worktree if `node_modules`/toolchains are stale.
- Your worktree is yours alone. Branch `lane/<lane>/<topic>` from fresh `origin/main`; one lane per branch (the pre-commit lane guard refuses other paths: `harness/harness.toml [lanes]`). Never bare `git stash`; WIP commits instead. Never `pkill -f`/`killall`.
- Tests first (a failing test commit, then the code). Markers `// @cpt-<kind>:<id>:p1` on the line before the code, IDs only from `**ID**:` lines; tick the CDSL step boxes you implement in the same PR. Never remove markers, skip tests, lower thresholds, edit generated files (`contracts/**`, `bindings.ts`: change `crates/noter-protocol`, `just contract-regen`) or harness files (`harness/`, `scripts/harness/`, `.github/`, `justfile`, test configs).
- Done = plain `just gate` exit 0 (check the real exit code). Then push, `gh pr create` (Conventional Commit title; body: what, how to verify, which spec items it ticks), run `/cf-sdlc-pr-review <N>` with `/ponytail-review` merged in, then `just review-publish <N>` (auto-merge). Loop on REQUEST CHANGES. Never merge by hand. Do not rebase or "Update branch" a PR without a conflict.
- Before opening a PR: `gh pr list --state open` must be < 10 across the repo and you must have < 2 open. Finish before starting.
- Report to the Teamlead through your preamble's commands: heartbeat every 5 min with a phase; `worker_done` once per task with the PR numbers, what merged, what is left; `ask` for a blocking question; `check` at every checkpoint. Product/spec ambiguity → HoD (`send --to dispatch:<HoD id in ROSTER>`); a blocker without an owner → Unblocker; a stuck PR → Babysitter; CI → DevOps.
- Middle developers (Sonnet): after two honest attempts at a red `just gate`/CI check, blocking review finding or QA FAIL, send the Teamlead the failing output; a senior pairs with you until it is green.
- QA checks every PR; answer QA FAIL items in the PR, not in chat.
