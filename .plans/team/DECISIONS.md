## D-19 2026-10-18 System audio permission is re-checked by a bounded probe on activation (option A)

Context: Backend Teamlead, for #43. The M0 story (`first-run-complete-setup`, Error — System audio not allowed) and DESIGN.md (permission-check row: "checks again when Noter becomes active"; 1291; 8326; 9177) expect the row to go **Checking…** then **Granted** by itself after the user grants System Audio Recording in System Settings. macOS has no API to read that permission; the core learns it only from a self-test or the `permission_request` probe. Options: A) probe once on activation while the row is denied; B) a **Check again** button (story and design change).
Decision: A, as DESIGN already says. Bounds: the probe runs once per app activation (and once on the native permission-change notice), only while the first-run Permissions step or the Settings permission row shows the system-audio row as denied, never while a capture runs, and it ends within about 3 s; the row shows **Checking…** from `setup:changed` and then **Granted** or stays **not allowed yet**. Engineering caveat for be-eng-2: a granted permission with nothing playing yields exact digital zeros, which the core reads as `zero_buffers` = denied, so a `play_clip: false` probe would keep a freshly granted row at "not allowed yet" in the common case (the user returns from System Settings with nothing playing). The probe must produce a non-zero system buffer itself (play the short test clip, as **Play Test Clip** does) or otherwise distinguish silence from denial; own-sound leak detection does not apply to the probe. If playing the clip on activation is judged too intrusive outside first run, limit the activation probe to the first-run step and leave the Settings row to **Run Test**. Not a PRD delta.
Acts: Backend Teamlead (be-eng-2 in #43). UI: nothing (DESIGN and first-run.md `inst-checking` already match).
