## Context and Problem Statement

Noter is developed UI-first: the frontend team builds every screen of `docs/DESIGN.md` while the Rust core is written in parallel by one part-time builder. DESIGN.md 3.3 names operation groups but leaves exact command, event and stream names to the core, and PM-09 says UI types are generated from the core's types. The UI cannot wait for the core to exist before it has types, and the two sides must not drift. Where does the contract live, and how does each side consume it?

## Decision Drivers

* The UI needs exact, typed names and shapes on day one, before the core has any logic.
* One source of truth; no hand-kept duplicates on either side (PM-09).
* The contract must build and be checked in CI on any machine, including Linux runners without WebKit.
* The core team writes Rust; the engine team writes Swift; the agents call JSON Schema tools.
* The UI must be able to run screens and stories without a Tauri build.

## Considered Options

* Rust types in `noter-protocol`, specta for TypeScript, our exporter for the client
* tauri-specta inside the app crate
* JSON Schema first, both sides generated
* A contract document, types written by hand on each side

## Decision Outcome

Chosen option: "Rust types in noter-protocol, specta for TypeScript, our exporter for the client", because it meets PM-09 literally (UI types come from the core's types), it exists before any core logic does, and it builds anywhere since the crate has no Tauri dependency. The registry macro in the crate also declares the `CoreApi` trait the core implements and the manifest the window-scope guard reads, so the names cannot diverge between the UI, the IPC host and the core. Engine, noter-mcp and skill contracts live in the same crate and are exported as JSON Schema with schemars.

### Consequences

* Good, because the UI imports generated `bindings.ts` and a typed `createCore()` client today, and runs against a fake core built on the same types.
* Good, because fixtures are Rust values: if a type changes, the fixtures stop compiling, so the fake cannot drift.
* Good, because one PR changes the contract for every consumer, and CI fails if a generated file is stale.
* Bad, because specta 2 is a release candidate; it is pinned exactly and only this crate uses it.
* Bad, because the command client is generated by our exporter instead of tauri-specta; the IPC host must keep handler parity with `COMMANDS`, enforced by a test.
* Neutral, because generated files are committed; reviewers read diffs of `bindings.ts` and the manifest.

### Confirmation

`noter-contract-export --check` in CI; `cargo test -p noter-protocol` (contract tests); `tsc` over `apps/desktop/src/core` and `contract.smoke.ts` against the fake; from M0, a test in `src-tauri` that the registered handlers equal `COMMANDS` and that each window's capability allows exactly its commands.

## Pros and Cons of the Options

### Rust types in noter-protocol, specta for TypeScript, our exporter for the client

The registry macro lists every command with arguments, result, Channel, group, stability and windows; types derive `specta::Type`; `noter-contract-export` writes the TypeScript, the manifest, the JSON Schemas and the fixtures.

* Good, because the contract is executable Rust the core compiles against.
* Good, because it needs no Tauri, WebKit or app build.
* Neutral, because the client code is ours (about 150 lines of generator).
* Bad, because two tools (specta and schemars) derive on some shared types.

### tauri-specta inside the app crate

`#[tauri::command]` functions with `#[specta::specta]`, collected by tauri-specta, which generates typed commands and events.

* Good, because it is the standard Tauri path and generates the client.
* Bad, because the types exist only once the command functions exist in the app crate, which the UI-first plan does not have yet.
* Bad, because it needs the Tauri dependency graph (WebKit on Linux) to build the bindings.

### JSON Schema first, both sides generated

Schemas in `contracts/`, Rust and TypeScript generated from them.

* Good, because neither language owns the contract.
* Bad, because Rust code generated from JSON Schema is poor at tagged unions and newtypes, and the core loses compile-time ownership.
* Bad, because more tooling for a small team.

### A contract document, types written by hand on each side

* Good, because it is fastest to start.
* Bad, because it drifts, which is exactly what UI-first parallel work cannot afford.

## More Information

Versions pinned: specta `2.0.0-rc.25`, specta-typescript and specta-serde `0.0.12`, schemars 1. When tauri-specta can collect commands from a Tauri-free crate, the generated client can switch to it without changing the contract.
